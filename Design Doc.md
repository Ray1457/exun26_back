## 1. Scope and assumptions

This plan covers the backend half of the sketch: Postgres schema, auth, storage, realtime, seed data and the /lib/data layer that Samaira's frontend calls. Frontend, computer vision and the 3D arcade are out of scope.

Assumptions (all listed again in section 13 so you can overrule them):

- Lens runs in the browser and sends its results to the backend. The backend stores findings and never does OCR or CV.
- The answer key (which clues connect, and why) lives only on the server. The client asks 'do these two pins connect?' and gets a verdict plus an explanation.
- The schema is multi-case, so new Exun files later need no migration.
- Map positions are normalised 0 to 100 values on the nuxEland map, not GPS, because the city is fictional.
- The seven files in the brief (Case Debrief, Transcript A, Energy Usage Dossier, Asset Integrity Report, Progress Assessment Log, original and altered code) are the seed corpus.

## 2. Platforms and architecture

```
Browser (Next.js on Vercel)
   └─ /lib/data  (typed wrapper, Result<T>)
        └─ Supabase (Mumbai, ap-south-1)
             ├─ Auth        email + password, demo account
             ├─ PostgREST   table reads, RPC for all writes that need rules
             ├─ Realtime    sightings, case files, progress, badges
             ├─ Storage     case-files, agent-uploads, avatars
             └─ Postgres    RLS, triggers, pg_cron
```

| Concern | Platform | Why |
| --- | --- | --- |
| Database, auth, storage, realtime | Supabase (hosted Postgres) | One service covers all four, row level security fits per-agent boards, free tier is enough for a demo, Mumbai region is closest to Delhi |
| Scheduled jobs | pg\_cron (Supabase extension) | Nightly demo reset, no extra server |
| Frontend hosting | Vercel (already in idea.md) | Preview deploy per pull request |
| CI/CD | GitHub Actions + Supabase CLI | Runs migrations and tests, pushes to staging and production |
| Local development | Supabase CLI + Docker | Full stack on your laptop, `supabase db reset` rebuilds from migrations and seed |
| Error tracking (optional) | Sentry free tier | Catches RPC failures during the demo |

Why not the alternatives: Firebase has no relational model or SQL-level security rules, which hurts the pins/connections/progress logic. Neon plus a separate auth, storage and realtime stack means four vendors to wire together. PocketBase on Fly works but you would own hosting and backups.

**Environments:** local, staging (a second free Supabase project, optional) and production.

| Variable | Where | Notes |
| --- | --- | --- |
| NEXT\_PUBLIC\_SUPABASE\_URL | Vercel, local | Public |
| NEXT\_PUBLIC\_SUPABASE\_ANON\_KEY | Vercel, local | Public key, safe only because every table has RLS (the dashboard may call it the publishable key) |
| SUPABASE\_SERVICE\_ROLE\_KEY | CI and seed script only | Never in the browser, never in a NEXT\_PUBLIC\_ variable |
| DEMO\_EMAIL, DEMO\_PASSWORD | Vercel server env, seed script | Used by the demo login button |
| NEXT\_PUBLIC\_USE\_MOCK\_DATA | local | Serves fixtures so Samaira is never blocked |

**Free tier caveats** (check current limits on supabase.com/pricing): projects pause after a period of inactivity, so a weekly keep-alive GitHub Action pings the REST endpoint; storage and database size are capped; Realtime has a concurrent connection cap, which matters if many judges open the site at once.

## 4. Data model

Tables: agents, cases, case\_files, energy\_readings, cabinets, sightings, findings, clue\_nodes, clue\_links, pins, connections, case\_progress, activity, badges, agent\_badges. One view: energy\_readings\_analyzed.

Rules that apply everywhere: primary keys are uuid with gen\_random\_uuid(), timestamps are timestamptz, every FK column gets an index, and every table has RLS enabled (section 6).

Signup trigger (app\_metadata can only be set through the admin API, so a user cannot make themselves a demo agent):

```sql
create function handle_new_user() returns trigger language plpgsql
security definer set search_path = '' as $$
declare v_name text := left(regexp_replace(coalesce(new.raw_user_meta_data->>'codename',''),
                                           '[^A-Za-z0-9_-]', '', 'g'), 24);
begin
  if length(v_name) < 3 or exists (select 1 from public.agents where codename = v_name) then
    v_name := 'agent_' || substr(replace(new.id::text, '-', ''), 1, 8);
  end if;
  insert into public.agents (id, codename, is_demo)
  values (new.id, v_name, coalesce((new.raw_app_meta_data->>'is_demo')::boolean, false));
  return new;
end $$;
create trigger on_auth_user_created after insert on auth.users
```

### 4.3 Evidence, map and findings

```sql
create table energy_readings (
  id                 bigint generated always as identity primary key,
  case_id            uuid not null references cases(id) on delete cascade,
  source_file_id     uuid references case_files(id),
  day_no             smallint not null,
  reading_date       date not null,
  meter_kwh          numeric(10,2) not null,
  reported_usage_kwh numeric(10,2) not null,
  highlighted        boolean not null default false,   -- rows 13 and 14 are yellow in the dossier
  unique (case_id, day_no), unique (case_id, reading_date)
);

create view energy_readings_analyzed with (security_invoker = true) as
with d as (
  select e.*, meter_kwh - lag(meter_kwh) over (partition by case_id order by reading_date) as meter_delta_kwh
  from energy_readings e),
m as (
  select case_id, percentile_cont(0.5) within group (order by reported_usage_kwh) as median_kwh
  from energy_readings group by case_id)
select d.*, m.median_kwh,
  (meter_delta_kwh is not null and abs(meter_delta_kwh - reported_usage_kwh) > 0.05) as is_discrepancy,
  (coalesce(meter_delta_kwh, reported_usage_kwh) > 10 * m.median_kwh)               as is_spike
from d join m using (case_id);

create table cabinets (
  id         uuid primary key default gen_random_uuid(),
```

## 6. Security

**Auth.** Email and password through Supabase Auth. The demo button signs in with DEMO\_EMAIL and DEMO\_PASSWORD (account created by `create-demo-user.ts` through the admin API with email confirmation skipped). A nightly pg\_cron job resets the demo agent. One shared demo account means judges edit the same board at once; if that bites, switch the button to Supabase anonymous sign-in, which gives each visitor an isolated agent with the same seed. Both are about 20 lines in agents.ts.

**RLS matrix** (the anon role gets nothing anywhere; 'RPC only' means no INSERT/UPDATE/DELETE grant at all):

| Table | Select | Insert | Update | Delete |
| --- | --- | --- | --- | --- |
| agents | own row | trigger only | own, columns codename, full\_name, avatar\_path only | no |
| cases, cabinets, energy\_readings | authenticated | service role | service role | service role |
| case\_files | official or own | own, kind upload, bucket agent-uploads | no | own uploads |
| findings | own | RPC only (save\_findings) | no | own |
| sightings | verified, or own unverified | RPC only (report\_sighting) | service role (verification) | service role |
| clue\_nodes, clue\_links | nobody | service role | service role | service role |
| pins | own | own, target must be visible to the agent | own, columns pos\_x, pos\_y, note only | own |
| connections | own | RPC only (create\_connection) | no | own |
| case\_progress, activity, agent\_badges | own | triggers and RPC only | no | no |
| badges | authenticated | service role | service role | service role |

Key policies:

```sql
alter table pins enable row level security;
create policy pins_select on pins for select to authenticated using (agent_id = (select auth.uid()));
create policy pins_insert on pins for insert to authenticated with check (
  agent_id = (select auth.uid()) and (
    (finding_id  is not null and exists (select 1 from findings f
        where f.id = finding_id and f.agent_id = (select auth.uid())))
    or cabinet_id is not null
    or (sighting_id is not null and exists (select 1 from sightings s
        where s.id = sighting_id and (s.status = 'verified' or s.reported_by = (select auth.uid()))))));
create policy pins_update on pins for update to authenticated
  using (agent_id = (select auth.uid())) with check (agent_id = (select auth.uid()));
create policy pins_delete on pins for delete to authenticated using (agent_id = (select auth.uid()));
revoke update on pins from authenticated;
grant  update (pos_x, pos_y, note) on pins to authenticated;

create policy case_files_select on case_files for select to authenticated
  using (owner_id is null or owner_id = (select auth.uid()));
create policy case_files_insert on case_files for insert to authenticated
  with check (owner_id = (select auth.uid()) and kind = 'upload' and bucket = 'agent-uploads');
```

**Trust boundary, stated honestly.** Lens runs on the client, so a determined user can post a forged finding and walk straight to a solved case. Mitigations in order of cost: (1) the answer key is hidden, so forging needs the story already; (2) `create_connection` is rate limited against brute-forcing pairs; (3) `save_findings` re-verifies what the server can check cheaply and sets `verified = true`: the Base32 machine ID decode, the energy spike and discrepancy (straight from the view), and the missing-class, clamp and orphaned-include checks from the stored source text. The theory meter can count only verified findings if you want it strict. For a hackathon (1) and (2) are enough.

**Other rules.** Every SECURITY DEFINER function sets `search_path = ''` and schema-qualifies its tables. The service role key stays out of the browser. Uploads are limited to 20 MB and an allowlist of pdf, png, jpeg, webp and plain text.

## 7. Server logic

All writes with rules go through RPCs (Postgres functions) called with `supabase.rpc()`.

| RPC | Arguments | Returns | Behaviour and errors |
| --- | --- | --- | --- |
| save\_findings | p\_case uuid, p\_findings jsonb (max 200) | setof findings | Upsert on (agent\_id, case\_id, finding\_key). Keeps the higher confidence. Runs the cheap server verifiers. Errors: invalid\_payload |
| create\_connection | p\_from uuid, p\_to uuid | connections | Described below |
| move\_pins | p\_moves jsonb (max 100 of {id,x,y}) | void | Updates only the caller's pins, silently skips others |
| report\_sighting | p\_case, p\_label, p\_x, p\_y, p\_seen\_at, p\_cabinet, p\_description | sightings | Inserts as unverified with reported\_by. Errors: invalid\_payload |
| get\_case\_progress | p\_case uuid | case\_progress | Creates the row on first call |
| log\_login | none | void | Writes a login activity row |
| simulate\_sighting | p\_case uuid | sightings | Demo or admin only. Inserts the next scripted verified sighting so Realtime can be shown live |
| reset\_demo\_agent | none | void | Demo or admin only. Wipes and re-seeds the demo agent. Errors: forbidden |

Error codes are raised as `raise exception '<code>' using errcode = '<sqlstate>'` and mapped to DataError.code in /lib/data: not\_authenticated, forbidden, pin\_not\_found, self\_connection, case\_mismatch, rate\_limited, invalid\_payload.

`create_connection` (sketch, the real one adds the rate limit check):

```sql
create function create_connection(p_from uuid, p_to uuid) returns public.connections
language plpgsql security definer set search_path = '' as $$
declare v_uid uuid := auth.uid(); a public.pins; b public.pins; l public.clue_links; c public.connections;
begin
  if v_uid is null then raise exception 'not_authenticated' using errcode = '28000'; end if;
  if p_from = p_to then raise exception 'self_connection' using errcode = '22023'; end if;
  select * into a from public.pins where id = p_from and agent_id = v_uid;
  select * into b from public.pins where id = p_to   and agent_id = v_uid;
  if a.id is null or b.id is null then raise exception 'pin_not_found' using errcode = 'P0002'; end if;
  if a.case_id <> b.case_id then raise exception 'case_mismatch' using errcode = '22023'; end if;
  -- rate limit: more than 20 invalid attempts in 60s raises 'rate_limited'
  if a.clue_key is not null and b.clue_key is not null then   -- least() ignores NULLs, so guard
    select * into l from public.clue_links
    where case_id = a.case_id and clue_a = least(a.clue_key, b.clue_key) and clue_b = greatest(a.clue_key, b.clue_key);
  end if;
  insert into public.connections (agent_id, case_id, from_pin, to_pin, link_id, is_valid, explanation)
  values (v_uid, a.case_id, least(a.id, b.id), greatest(a.id, b.id), l.id, l.id is not null, l.explanation)
  on conflict (from_pin, to_pin) do update set agent_id = excluded.agent_id   -- idempotent
  returning * into c;
  perform public.recompute_progress(v_uid, a.case_id);
  return c;
end $$;
```

`recompute_progress(agent, case)`: links\_found is the count of distinct valid link\_ids; theory\_pct is the weight of found links over the weight of all links times 100; solved\_at is set once every required link is found and is never cleared afterwards.

**Triggers**

| Trigger | On | Effect |
| --- | --- | --- |
| set\_updated\_at | agents | maintains updated\_at |
| pins\_set\_clue\_key | pins before insert | copies clue\_key from the finding (if finding\_key exists in clue\_nodes), cabinet or sighting; null otherwise |
| log\_activity\_\* | case\_files (uploads), findings, pins, connections, sightings (agent reports), case\_progress (solved\_at set) | inserts the matching activity row with a small payload |
| evaluate\_badges | activity after insert | runs the generic criteria check for that agent, inserts into agent\_badges on conflict do nothing, which logs badge\_earned |

**pg\_cron:** `select cron.schedule('reset-demo', '30 21 * * *', 'select public.reset_demo_agent_system()')` runs at 03:00 IST (UTC 21:30). Use an internal variant that skips the caller check, since cron has no JWT.

## 9. Realtime and storage

```sql
alter publication supabase_realtime add table sightings, case_files, case_progress, agent_badges, activity;

insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types) values
  ('case-files',    'case-files',    false, 20971520, array['application/pdf','text/plain','image/png','image/jpeg']),
  ('agent-uploads', 'agent-uploads', false, 20971520, array['application/pdf','text/plain','image/png','image/jpeg','image/webp']),
  ('avatars',       'avatars',       true,  2097152,  array['image/png','image/jpeg','image/webp']);

create policy evidence_read on storage.objects for select to authenticated using (bucket_id = 'case-files');
create policy uploads_own  on storage.objects for all to authenticated
  using      (bucket_id = 'agent-uploads' and (storage.foldername(name))[1] = (select auth.uid())::text)
  with check (bucket_id = 'agent-uploads' and (storage.foldername(name))[1] = (select auth.uid())::text);
```

Upload path convention is `agent-uploads/{agent_id}/{uuid}-{filename}`. Realtime postgres\_changes respects each table's select policy, so an agent only receives sightings they may see and only their own progress and badge events. Channel names: `case:{caseId}:sightings`, `case:{caseId}:files`, `agent:{agentId}:progress`, `agent:{agentId}:badges`. The client deduplicates events by id and re-fetches on reconnect.

## 10. Testing strategy

Five layers, each run by one command, all green before anything reaches production.

| Layer | Tool | Runs against | Command |
| --- | --- | --- | --- |
| Database (schema, seed, RLS, triggers, RPCs, badges, cron functions) | pgTAP + supabase\_test\_helpers | local Supabase Postgres | `supabase test db` |
| /lib/data unit tests | Vitest with a mocked supabase-js | nothing external | `npm run test:unit` |
| Seed content tests | Vitest | seed.sql output and the source PDFs | `npm run test:seed` |
| Integration | Vitest | `supabase start` (real Auth, Storage, Realtime) | `npm run test:integration` |
| Load smoke (optional) | k6 | local or staging | `npm run test:load` |

The heaviest weight sits on the database layer because the rules live there: RLS, RPCs and triggers. A test that only mocks the client cannot catch a policy hole.

**Coverage gates.** Every policy in `pg_policies` must have both an allow test and a deny test (a small script lists policies and fails if a policy name is not referenced in tests/). Every RPC error code has at least one test. /lib/data needs 85 percent line coverage.

## 11. CI/CD and environments

```yaml
name: backend-ci
on: [pull_request, push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: supabase/setup-cli@v1
      - run: supabase start
      - run: supabase db reset
      - run: supabase db lint
      - run: supabase test db
      - run: supabase gen types typescript --local > lib/data/types.gen.ts && git diff --exit-code lib/data/types.gen.ts
      - run: npm ci && npm run test:unit && npm run test:seed && npm run test:integration
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    environment: production        # requires manual approval
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: supabase/setup-cli@v1
      - run: supabase link --project-ref ${{ secrets.SUPABASE_PROJECT_REF }}
      - run: supabase db push
        env: { SUPABASE_ACCESS_TOKEN: '${{ secrets.SUPABASE_ACCESS_TOKEN }}', SUPABASE_DB_PASSWORD: '${{ secrets.SUPABASE_DB_PASSWORD }}' }
```

A second workflow, `keepalive.yml`, runs weekly and requests `/rest/v1/cases?select=id&limit=1` with the anon key so a free project never pauses before judging.

Workflow rules: schema changes happen only through migration files, never in the dashboard; `supabase db diff` is used to generate them. Seed and demo-user scripts run once per environment after the first deploy. Take a manual `pg_dump` before demo day as a fallback.

## 13. Open questions and risks

Decisions I made that you may want to change:

1. **Shared demo account or per-visitor anonymous sessions.** Shared is simpler and matches your sketch; anonymous avoids judges overwriting each other. Either is a small change in agents.ts.
2. **Answer key.** The 13 links in section 5 are my reading of idea.md. Confirm them with whoever owns the story, especially which ones are required for the case to count as solved.
3. **Cabinet and sighting seeds.** Only Wenoti and one sighting come from the files. The rest is placeholder; agree names, coordinates and counts with Samaira and Mittal.
4. **Strict or loose verification.** Whether the theory meter counts only server-verified findings (strict) or all findings (loose, my default).

Things in the case files worth a decision from the story side, because they touch seed data:

- idea.md says the character 'came back at 22:31', which is the same timestamp as the first sighting in Transcript A. The sighting seed needs a distinct return time or a clarification.
- The energy dossier covers Oct 26, but Nano's log is timestamped Oct 25 23:54. This is harmless for the backend, but a sharp reviewer may notice.
- Rows 13 and 14 (Oct 25 and 26) are highlighted yellow in the dossier with no explanation. I store this as `highlighted` so Lens can show it; decide whether it is a clue or just formatting.
- The code analysts' 'missing Character class' means the altered file would not compile as written. That is fine for the story, but the code-diff finding should describe it as removed rather than broken.
